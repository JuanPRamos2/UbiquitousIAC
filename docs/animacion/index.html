Cómo circulan JWT y Redis en la librería

Seis microservicios independientes comparten la misma URL de Redis y la misma clave HMAC. PostgreSQL guarda los datos. Redis guarda lo que caduca: sesión, refresh, revocación y caché del catálogo. El monolito Node no pasa por Redis.

fuente de verdad
  1. El radio de Tk elige HTTP o HTTPS y lo guarda. El valor inicial es HTTP.
  2. POST /login compara la contraseña con el hash bcrypt en PostgreSQL. No firma con esa contraseña.
  3. Login emite un JWT HS256 de 20 minutos con user_id, role_id y jti, usando JWT_SECRET_KEY.
  4. Guarda session:<jti> con el TTL del access token y refresh:<hash> con un TTL mayor. El refresh en claro se queda en el cliente.
  5. Cada escritura manda Authorization: Bearer. El servicio verifica firma, algoritmo, emisor, audiencia, expiración y claims.
  6. Después lee jwt:revoked:<jti>. Si la clave existe, responde 401. Si Redis no contesta, responde 503 y no modifica datos.
  7. Un administrador (role_id 1) puede dar de alta, cambiar y borrar. Un cliente solo ve sus pedidos y sus pagos, y solo cambia su propia contraseña con tres valores.
  8. GET /books y GET /books/{isbn} miran primero books:list:<filtros> o books:<isbn>. Si no está, leen PostgreSQL o el catálogo del proceso y guardan el resultado unos segundos.
  9. Un alta o un cambio de libro borra books:*. Lo mismo pasa con authors:*.
  10. Pedidos descuenta stock en la misma transacción. Pagos, en su propio proceso, marca el pedido como pagado. No se llaman por HTTP.
  11. POST /logout borra sesión y refresh, y escribe la revocación. El access token deja de servir aunque todavía no haya caducado.
  12. Si Redis cae, el catálogo público se sigue leyendo. Login, logout, refresh y cualquier operación que dependa de la revocación se detienen.
