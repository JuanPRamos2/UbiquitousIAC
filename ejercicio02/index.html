2 Objetivo y alcance

Diseñar, construir, probar, desplegar y documentar una aplicación web monolítica en Node.js para la gestión de una librería en línea, con acceso directo a PostgreSQL. El propósito no es solo “que funcione”, sino justificar decisiones de requisitos, datos, arquitectura, seguridad, pruebas y publicación.

La solución renderiza HTML en el servidor, administra usuarios registrados, implementa CRUD sobre el modelo normalizado, maneja imágenes de libros y registra conceptos y definiciones por libro.

Restricciones

  • Monolito server-side: Node.js, Express y EJS.
  • Acceso a PostgreSQL con pg y SQL parametrizado / stored procedures.
  • Sin REST, GraphQL, SOAP ni microservicios.
  • Sin JSON/XML como intercambio frontend–backend.
  • Máximo un Administrador, reforzado también en la base de datos.
  • Quien visita el sitio entra por el servidor web; la aplicación no se publica como un puerto interno abierto a Internet.

Actores

  • Visitante: login y registro. Sin catálogo.
  • Usuario registrado (client): catálogo, búsqueda, detalle. Sin CRUD.
  • Administrador: todo lo anterior más CRUD, imágenes, conceptos y usuarios. No puede crear un segundo admin.

Riesgos iniciales: acceso no autorizado, SQL Injection, uploads peligrosos, exposición de credenciales, borrado accidental y publicación de secretos.

4 Decisiones de arquitectura y diagrama del monolito

Flujo: Navegador → Apache/NGINX → Node.js/Express → módulos internos → PostgreSQL / disco uploads/. Presentación, lógica y datos viven en un solo proceso desplegable. Dividir carpetas no convierte esto en microservicios. El reverse proxy no es un servicio de negocio.

Tres decisiones mínimas (detalle en ENGINEERING_DECISIONS.md):

  1. Monolito server-side frente a SPA+API o microservicios: el enunciado pide HTML generado en el servidor y un equipo pequeño.
  2. SQL parametrizado + SP frente a ORM: hay que demostrar PK/FK/CHECK y pruebas negativas reales de PostgreSQL.
  3. EJS + formularios frente a JSON: cumple la restricción de intercambio y simplifica el despliegue.

5 Diseño de la base de datos, diagrama ER y 4FN

Síntesis completa: NORMALIZATION_4FN.md · plantilla de clase: NORMALIZATION_4FN.xlsx.

Relación inicial no normalizada (listas de autores, géneros, imágenes y conceptos). La definición depende de (Libro, Concepto), no solo del concepto.

  • 1FN: valores atómicos; desaparecen listas.
  • 2FN: BOOKS con atributos que dependen de la clave del libro.
  • 3FN/BCNF: catálogos FORMATS y CATEGORIES.
  • 4FN: MVDs independientes ISBN ↠ autor, género, imagen y concepto → tablas puente.

Puentes: book_authors, book_genres, book_images, book_concepts (definición, capítulo, página). El administrador único es cardinalidad sobre users.role = 'admin' (índice parcial + trigger), no una MVD.

7 Organización de la aplicación

La interfaz, las reglas de negocio y el acceso a datos se despliegan juntos. Por dentro hay separación de responsabilidades: arranque, rutas, servicios, permisos y plantillas. Las pantallas no consultan la base de datos de forma directa.

8 Funcionalidades implementadas

La persona usuaria envía un formulario; el servidor valida, aplica la regla de negocio y devuelve una página HTML.

  • Registro, login, logout y perfil.
  • Catálogo autenticado con búsqueda por ISBN y título.
  • CRUD de libros, autores, géneros, formatos, categorías y conceptos.
  • Relaciones libro–autor, libro–género y libro–concepto (definiciones IaaS, PaaS, SaaS, FaaS, etc. en el libro de Cloud Computing).
  • Carga JPG/PNG/WebP, texto alternativo y portada.

Para usarla ahora, sin la VM: abrir la librería en este sitio. Cuando el monolito esté en GCP, el acceso público /library se documentará aquí.

13 Decisiones de ingeniería, problemas y soluciones

Registro canónico: ENGINEERING_DECISIONS.md. Esquema: necesidad → alternativas → decisión → justificación → riesgo → evidencia.

  • D1 Monolito: una unidad desplegable. Riesgo: un segundo canal (móvil) tensionaría el corte.
  • D2 PostgreSQL directo: demuestra integridad. Riesgo: más SQL manual si el modelo crece.
  • D3 EJS: formularios HTML. Riesgo: menos interactividad; CSRF residual en POST.
  • D4 Un admin en BD: la UI puede eludirse; el índice/trigger no.
  • D5 Imágenes en disco: metadatos en PostgreSQL; el backup de solo BD pierde archivos.
Los problemas encontrados al publicar el servicio y cómo se resolvieron se documentarán aquí, sin datos de conexión.

15 Conclusiones y mejoras futuras

El monolito server-side cubre el escenario académico: un canal web, un equipo y una VM. La 4FN evita cartesianizar autores × géneros × imágenes. La seguridad se defiende en aplicación y en PostgreSQL.

Hacia componentes desacoplados cambiaría: contrato de API, autenticación entre servicios, despliegues independientes y observabilidad distribuida. No se cambia la arquitectura de este ejercicio; se documenta el trade-off.

  • Tokens CSRF explícitos además de SameSite.
  • Object storage si las imágenes superan el disco de la VM.
  • Cerrar evidencias T-01…T-30 en CentOS y publicar el .tar.gz sin secretos.
