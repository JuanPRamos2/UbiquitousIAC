1 Objetivo y scope

Diseñar, construir, probar y documentar un módulo SOAP independiente que se integre con la librería del ejercicio 02 sin modificar esa aplicación.

Incluido: consultar conceptos pendientes del catálogo real, registrar IaaS/PaaS/SaaS/FaaS, consultar progreso, registrar clientes atendidos, detectar duplicados con SOAP Fault y publicar un WSDL.

Fuera de alcance: migrar la librería, crear una API REST, reemplazar PostgreSQL, cambiar las tablas existentes o usar Spyne/Zeep para ocultar el Envelope en el módulo.

2 Arquitectura inicial y arquitectura final

Usuario → Escritorio → HTTP POST/XML → Módulo SOAP → PostgreSQL
Aplicación de librería → PostgreSQL (sin cambios)

3 Descripción de la librería y del módulo SOAP

La librería en línea (ejercicio 02) administra libros, conceptos, categorías y cuentas web. Este ejercicio no toca su código ni altera esas tablas.

El módulo SOAP es un componente nuevo. Publica el contrato, recibe Envelopes, valida, consulta el catálogo en modo lectura y escribe sólo en sus tablas propias: clasificadores, clasificaciones_cloud y clientes_servidos.

Las cuentas web de la librería no se reutilizan. Un clasificador SOAP se identifica con nombre, apellidos y correo.

5 Contrato WSDL y tipos XSD

El contrato vive en library-classifier.wsdl. Estilo document/literal wrapped. Namespace http://udem.edu.mx/iac/library-classifier.

El tipo CloudModelo es una enumeración XSD: IaaS, PaaS, SaaS y FaaS. Un valor como XaaS no entra al catálogo.

8 Seguridad y WS-Security

Las tres operaciones de clasificación identifican al usuario por correo. ObtenerEstadisticasPorModelo exige UsernameToken en el Header. La contraseña no se guarda en claro ni se publica en las evidencias (el Request usa ********).

En la demostración de Ubiquitous el usuario de laboratorio es soap_stats. La clave no se reutiliza en un servidor real.

9 Aplicaciones de escritorio como clientes SOAP

El clasificador Java del ejercicio 01 ahora tiene modo Cliente SOAP. Captura nombre, apellidos y correo. Construye el Envelope, lo envía al endpoint y muestra la respuesta o un mensaje claro si llega un Fault. No se conecta a PostgreSQL.

Puedes probar el mismo flujo en el navegador: probar.html.

12 Evidencias de PostgreSQL

Después de clasificar conceptos reales hay que verificar que llegaron a clasificaciones_cloud y que clientes_servidos cuenta las peticiones.

SELECT isbn, concept_id, modelo, tipo_cliente, created_at
FROM clasificaciones_cloud
ORDER BY id;

SELECT tipo_cliente, identificador, peticiones, ultima_peticion
FROM clientes_servidos;

13 Decisiones de ingeniería y trade-offs

SOAP y WSDL. Necesidad: contrato interoperable. Decisión: SOAP 1.1 document/literal. Ventaja: clientes generados. Limitación: un campo obligatorio nuevo rompe clientes viejos.

Envelope a mano. Necesidad: ver Header y Body. Decisión: XML construido nodo a nodo, sin concatenar texto. Ventaja: se escapan valores. Limitación: más verboso que un framework.

Tablas propias. Necesidad: no mezclar clasificadores con cuentas de la librería. Decisión: clasificadores separado. Ventaja: la librería sigue intacta. Limitación: dos identidades para la misma persona.

El resto está en ENGINEERING_DECISIONS.md.

14 Problemas encontrados y soluciones

  • Apache en Ubiquitous no deja Options en .htaccess. Esa directiva tumba la carpeta con HTTP 500. Se quitó. El módulo se prueba aquí en probar.html.
  • Un directorio anidado con su propio .git impedía git add. Se eliminó el repositorio interno.
  • El PDF mezcla ejercicio03 y ejercicio04. Este trabajo se publica como ejercicio03, que es la URL de la parte 11.

16 Uso de IA y prompts

Se usó un agente de código para revisar el sitio, completar el reporte, las cinco tareas y la página de prueba. Lo que se aceptó: estructura del reporte, WSDL, Faults y tablas de evidencias. Lo que se revisó a mano: que el contrato no filtre secretos y que Ubiquitous no publique .env. Lo que se rechazó: frameworks que generen el Envelope solos, y mencionar implementaciones internas que el enunciado no pide en las tareas.

Prompts: AI_USAGE.md.

17 Conclusiones

SOAP obliga a pensar el contrato antes que la pantalla. El WSDL dice qué se puede pedir, el Fault dice qué salió mal y WS-Security demuestra que el Header también es parte del mensaje.

El costo es verbosidad. El beneficio es que un cliente en otro lenguaje puede hablarle al mismo servicio sin conocer cómo está hecho por dentro.
