Parcial 1 · Ejercicio guiado 02

Tarea 2c: evaluación arquitectónica

Juan Pablo Ramos Salazar · 610248 · Integración de Aplicaciones Computacionales

Pregunta

¿Conviene una aplicación web unificada, generada en el servidor, para una librería académica de un solo canal y un equipo pequeño? La comparación cubre complejidad, despliegue, crecimiento, mantenimiento, seguridad y tamaño del equipo. El ejercicio no cambia de enfoque: se analizan los intercambios.

Ensayo

Para el desarrollo de la aplicación web de gestión de una librería considero que una arquitectura monolítica server-side es una decisión adecuada, principalmente por el alcance del proyecto, la cantidad de funcionalidades necesarias y el tamaño del equipo encargado de desarrollarlo. En este ejercicio, la aplicación debe manejar usuarios, autenticación, libros, autores, géneros, formatos, conceptos, imágenes, stock y precios, además de implementar un CRUD completo sobre las diferentes tablas de PostgreSQL. Todo esto debe realizarse utilizando Node.js, Express, EJS y acceso directo a PostgreSQL.

El principal beneficio del monolito es que toda la aplicación funciona como una sola unidad desplegable. El navegador realiza una solicitud que pasa por Apache o NGINX, llega a la aplicación Node.js y posteriormente es procesada por las rutas, controladores, servicios y middleware necesarios antes de acceder a PostgreSQL. Finalmente, Express renderiza una vista EJS y devuelve HTML al navegador. Aunque internamente exista una separación entre routes, services, middleware, views y config, todos estos elementos siguen formando parte de la misma aplicación. Esto facilita entender el flujo completo del sistema y disminuye la cantidad de infraestructura necesaria.

La complejidad operativa también es considerablemente menor en comparación con una arquitectura de microservicios. En el proyecto solamente necesitamos desplegar una aplicación Node.js, una base de datos PostgreSQL y configurar Apache o NGINX como reverse proxy. Si se utilizaran microservicios, podrían existir servicios independientes para usuarios, libros, imágenes, autenticación o inventario. Cada uno tendría que ser desplegado, configurado, monitoreado y comunicado con los demás. Para un proyecto académico y un equipo pequeño, esto aumentaría la cantidad de trabajo sin aportar un beneficio proporcional.

Una arquitectura desacoplada por componentes podría tener algunas ventajas. Por ejemplo, se podría separar completamente el frontend del backend, permitiendo que ambos evolucionaran de manera independiente. El backend podría exponer una API y el frontend consumirla utilizando tecnologías como React o Angular. Sin embargo, esto también introduciría nuevos problemas. Se necesitaría desarrollar y asegurar una API, manejar mecanismos de intercambio de información y posiblemente configurar políticas adicionales de autenticación, autorización y comunicación entre sistemas. En este ejercicio en particular, estas características aumentarían la complejidad sin ser necesarias para cumplir con los requisitos principales.

En cuanto a escalabilidad, los microservicios tienen una ventaja importante cuando un sistema alcanza una gran cantidad de usuarios. Si una sección del sistema recibe muchas solicitudes, solamente ese servicio puede escalarse. Por ejemplo, en una librería comercial grande podría ser necesario escalar el catálogo independientemente de la administración de usuarios. En nuestro caso, la aplicación tiene un alcance limitado y no está diseñada para manejar millones de solicitudes, por lo que escalar todo el monolito sería suficiente.

La seguridad también resulta más sencilla de controlar dentro de una sola aplicación. El proyecto requiere sesiones, autorización por roles, consultas SQL parametrizadas, validación de archivos, protección de contraseñas y manejo seguro de credenciales. Al mantener todo dentro del monolito existe un menor número de puntos de comunicación que proteger. En una arquitectura distribuida también habría que asegurar la comunicación entre servicios y administrar más configuraciones y credenciales.

El principal riesgo del monolito aparece cuando el proyecto crece demasiado. Con el tiempo puede convertirse en una aplicación difícil de mantener si no existe una buena organización del código. Por esta razón, considero importante mantener la separación entre rutas, lógica de negocio, middleware, acceso a datos y vistas desde el inicio.

En conclusión, para este ejercicio el monolito server-side representa un buen equilibrio entre simplicidad, seguridad, mantenimiento y facilidad de despliegue. Los microservicios o una arquitectura completamente desacoplada podrían ser mejores en un sistema mucho más grande, con varios equipos de desarrollo y necesidades independientes de escalabilidad. Sin embargo, para la librería planteada, añadir esa complejidad sería innecesario. La arquitectura seleccionada permite concentrarse en desarrollar correctamente las funcionalidades y demostrar el funcionamiento completo del sistema sin introducir infraestructura que el problema actualmente no requiere.
